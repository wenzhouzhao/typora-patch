# Typora Windows 补丁通用方法论(任意版本 · 任意机器)

> **定位**:这是一份**方法论手册**——不绑定具体版本号、安装路径或某台电脑,
> 目标是:拿到任意新版本的 Typora for Windows,都能从零完成"分析 → 补丁 → 验证 →
> 一键化 → 制作预打补丁安装包"的完整流程。
> 本项目 1.14.9 的具体实现作为实例穿插在文中(标注 **例**)。
>
> 配套文档(同目录):`使用教程.md`(日常操作)、`Typora_1.14.9_Patch_Guide.md`
> (1.14.9 技术参考)、`过程记录.md`(1.14.9 实施时间线)。
>
> **适用边界**:仅用于对自己已合法安装的副本做本地修改与个人使用,
> 不应将打完补丁的安装包向他人分发。

## 〇、方法论总图

```
┌ 侦查 ────────────┐   ┌ 完整性机制 ──────┐   ┌ 补丁设计 ─────────┐
│ ① 确认架构与版本  │ → │ ④ exe 内嵌哈希    │ → │ ⑥ 许可逻辑三条路线 │
│ ② asar 结构      │   │ ⑤ 应用自检 [LC]  │   │ ⑦ 字节码锚点补丁   │
│ ③ 明文/字节码比例 │   └──────────────────┘   │ ⑧ fs 钩子抗自检    │
└──────────────────┘                          └───────────────────┘
        ↓                                            ↓
┌ 重打包与哈希 ─────┐   ┌ 验证 ────────────┐   ┌ 工程化 ───────────┐
│ ⑨ asar 解包/重打包│ → │ ⑫ 验证清单        │ ← │ ⑩ 一键 bat        │
│ ⑩ exe 哈希原位替换│   │ ⑬ 故障排查矩阵    │   │ ⑪ Inno 安装包     │
└──────────────────┘   └──────────────────┘   └───────────────────┘
```

核心思想一句话:**Electron 应用的"不可改"只有两层——exe 内嵌的 asar 头哈希、
以及应用启动自检;把这两层看透,asar 里的明文 JS 就是任意大的后门。**
字节码(.jsc)改不了就绕:运行时钩子覆盖行为,或对字节码做同长度字节替换。

## 一、阶段① 侦查:确认架构与版本

### 1.1 需要回答的问题

1. 是不是 Electron 应用?(看安装目录:`*.dll`(ffmpeg.dll、libGLESv2.dll)、
   `resources\app.asar`、`locales\`、`*.pak` → 是)
2. Electron / Chromium / V8 版本?(**例**:1.14.9 = Electron 42.2.0 / Chromium 148 /
   V8 14.8;版本号可从 `resources\app.asar` 里 `package.json`,或 exe 属性、
   运行日志中获得)
3. `resources\app.asar` 里有几个文件?比例如何?
   - 全明文 JS → 最理想,直接改
   - 混合:`launch.dist.js`(明文)+ `atom.compiled.dist.jsc`(V8 字节码)→
     Typora 的典型形态,明文入口是救命稻草(见阶段⑥)
   - 全字节码且无明文入口 → 只能钩 Node 原生模块或字节码补丁,难度最高

### 1.2 asar 解包的三种办法(任选)

```bat
:: 办法 A: 官方工具 (需要 node)
npx asar extract resources\app.asar <输出目录>

:: 办法 B: 7-Zip 21.07+ 可直接打开 asar
:: 办法 C: 自写解析器 (见第四节 §4.1, 补丁脚本里已含 parseAsarHeader)
```

解包后重点看:入口(`package.json` 的 `main`)、入口文件的加载方式、
`node_modules`(哪些原生模块,例如 Typora 的 `native-reg`)。

### 1.3 判断"许可证逻辑在哪"

通用线索(按命中概率排序):

| 线索 | 在哪找 | 典型产物 |
|---|---|---|
| `license` 字符串 | asar 内明文 JS / html 资源 | `license.html`、许可页路由 |
| `trial` / `dayRemains` / `expire` | 明文 JS、jsc 字符串 | 试用天数计算 |
| 注册表/文件读写 | 原生模块 + 字符串(`IDate`、`SLicense`、`Registration`) | 许可状态存储位置 |
| 原生模块 | `node_modules` 下带 `.node` 的 | **例**:`native-reg`(读 Windows 注册表) |

**例(Typora)**:许可状态在 `HKCU\Software\Typora`(`IDate`=试用起点,
`SLicense`=许可证);试用 = IDate + 15 天;到期/未激活时主进程
`loadURL("typora://app/typemark/page-dist/license.html?...dayRemains=N&needLicense=true")`
弹独立窗口。

> 通用技巧:把注册表 `IDate` 类键值改成过去的时间再启动,观察行为变化,
> 是验证"找到了试用起点"的最快手段(改回去即可)。

## 二、阶段② 完整性机制定位(决定补丁可行性的关键)

任意 Electron 发行版都可能有以下 0~N 层校验,**逐层确认并给出对策**才算侦查完成:

### 2.1 exe 内嵌 asar 完整性(Electron fuse)

- **是什么**:Electron 的 `EnableEmbeddedAsarIntegrityValidation` fuse,
  exe 内嵌 JSON:`[{"file":"resources\\app.asar","alg":"SHA256","value":"<64位hex>"}]`,
  其中 value = **asar 头 JSON 字符串(不含 4 字节对齐填充)的 sha256**。
- **怎么找**:在 exe 二进制里搜 `app.asar` 或 `"alg":"SHA256"`;
  正则模板(注意反斜杠转义层数,不同版本可能不同):
  ```
  ("file":"resources\\\\app\.asar","alg":"SHA256","value":")([0-9a-f]{64})(")
  ```
  **例**:1.14.9 恰为此格式。若搜不到,先搜 `app\.asar` 扩大范围再观察上下文。
- **对策**:改完 asar 后**定长原位替换**该 hex(以 latin1 读 exe、replace、写回,
  断言替换前后文件长度不变)。永不改 PE 结构。

### 2.2 应用启动自检(如有)

- **是什么**:应用代码在启动早期(约 1 秒内)读自己的关键文件比对完整性,
  失败则静默退出。**例**:Typora 主进程 jsc 读 `app.asar/package.json` 与
  `launch.dist.js` 比对,日志记 `Integrity check failed` 后退出。
- **怎么发现**:补丁后启动秒退 → 查日志(`%APPDATA%\<应用>\*.log`)→
  在 jsc/明文里搜 `Integrity`、`checkFailed` 等字符串。
- **对策**:fs 钩子——在自检发生前劫持 `fs.readFileSync` / `fs.promises.readFile`,
  对自检读取的路径返回**剥掉补丁标记的原始内容**(见 §5.3)。
  ⚠ 顺序很重要:钩子必须在入口 JS 的最早时刻安装(见 §5.1 注入点)。

### 2.3 其他常见层(本应用未用,遇到再对号)

代码签名校验(改了就重签或放弃 exe 修改)、远端服务器校验(需改网络层)、
`resources\app` 目录模式禁用(Electron 优先读 `app` 目录——若发行版禁止,
只能走 asar;**例**:Typora 的 fuse 禁用了目录模式)。

## 三、阶段③ 补丁设计:许可逻辑的三条路线

按优先级从高到低,通常组合使用:

### 路线 A:运行时钩子(首选,不改字节码)

利用"入口是明文 JS"这一事实,在**主进程字节码加载之前**注入一段 JS,
对后续 require 的模块做运行时劫持。注入点:

```
在明文入口文件中,把
    require("./主程序.jsc");          ← 末尾的最终 require
替换为
    require("<补丁模块>"),require("./主程序.jsc");
```

(用逗号表达式保持语法正确;幂等性靠正则剥旧注入实现。)

补丁模块的标准骨架(全部只用 Node 内置模块,任何 node 版本可跑):

```js
(function () {
  var DEBUG = process.env.<应用>_PATCH_DEBUG === "1";
  function L() { /* 拼接 + appendFileSync 到 %TEMP% 日志 */ }

  var Module = require("module");
  var origLoad = Module._load;
  Module._load = function (request, parent, isMain) {
    var m = origLoad.apply(this, arguments);
    try {
      // 钩 1: 原生注册表模块 → 试用起点虚拟化
      if (request.indexOf("native-reg") >= 0 && m && !m.__hooked) {
        m.__hooked = true;
        ["getValue", "queryValue"].forEach(function (fname) {
          var orig = m[fname];
          if (typeof orig !== "function") return;
          m[fname] = function () {
            var out = orig.apply(this, arguments);
            // 找出参数里的值名 (最后一个 string 参数)
            var name = null;
            for (var i = arguments.length - 1; i >= 0; i--)
              if (typeof arguments[i] === "string") { name = arguments[i]; break; }
            if (name === "IDate") return <今天日期 M/D/YYYY>;   // 虚拟化试用起点
            return out;
          };
        });
      }
      // 钩 2: fs → 自检返回原始内容 (§2.2 的对策)
      if (request === "fs" && m && !m.__hooked) { /* 包 readFileSync/promises.readFile */ }
      // 钩 3: electron → 丢许可窗口
      if (request === "electron" && m && !m.__hooked) { /* 见 §5.2 */ }
    } catch (e) { L("hook error", e && e.stack); }   // ⚠ 必须吞异常, 见 §7 已知噪声
    return m;
  };
})();
```

三个钩子的要点:

1. **试用起点虚拟化**:钩原生注册表模块的取值函数,命中"试用起点"值名时返回当天。
   效果:试用天数恒满,永不过期(等价于 Mac 补丁的 `cannotContonueUse → 0`)。
2. **许可窗口拦截**:钩 `BrowserWindow.prototype.loadURL`,URL 含 `license.html`
   时**不加载并隐藏空壳窗口**(setTimeout 内 `hide()` + `setSkipTaskbar(true)`,
   再钩 `show` 拦掉展示);同时钩 `webContents.prototype.loadURL` 兜底。
   ⚠ **只能藏,不能 destroy**——销毁最后一个窗口会触发 `window-all-closed`
   导致整个应用退出。
3. **fs 抗自检**:对 §2.2 定位到的自检读取路径,返回原始内容。

**已知噪声(勿误判为故障)**:原生模块第一次 require 命中的可能是其 index.js
的冻结 exports,给函数赋值会抛 `Cannot assign to read only property`,
被 try/catch 吞掉即可;真正的绑定模块在后续 require 时会再次命中并成功挂钩
(以日志里出现"override 生效"为准,不要以有无 error 行为准)。

### 路线 B:字节码同长度补丁(对付嵌在 .jsc 里的行为)

V8 字节码(.jsc / cachedData)**不能重编译、不能改长度**,但可以做**同长度字节替换**。
通用流程:

1. `strings` / 二进制搜索特征串(候选:`UNREGISTERED`、`hasLicense`、`license.html`、
   `option`)。
   **例**:水印按钮的注入代码整段嵌在主字节码里,常量池含
   `UNREGISTERED` 与 `File.option.hasLicense = false;`。
2. 定位锚点:先找唯一的长字符串,再在其**前若干字节**窗口内找条件/调用结构。
3. 构造**等长**替换,使该行为分支恒不执行:
   - 条件恒假:`window.File.option` → `window.File.optio0`(`option`→`optio0`,6→6 字符,
     undefined 恒 falsy,整段创建水印的代码被跳过)
   - 同理可用的等长手筋:`license`→`licens0`、`options`→`option0` 等(自造不存在的属性名)
4. 三重防护写进脚本:锚点找不到 → **中止并报错**(宁可失败也不打坏文件);
   已是补过形态 → 跳过(幂等);两处锚点至少一处命中才继续。
5. **为什么必须等长**:V8 cachedData 带长度/哈希自描述,变长会导致
   `cachedDataRejected` 或常量池错位;等长替换不影响任何偏移。

### 路线 C:状态层(辅助)

直接操作许可状态存储(注册表/文件),用于**验证**而非依赖:改坏 `IDate` 观察弹窗、
删键重置试用。补丁本体不应依赖它(应用可能启动即重写)。

## 四、阶段④ asar 重打包与 exe 哈希替换(任意版本通用算法)

### 4.1 asar 格式与手写重打包

```
asar 文件布局:
  [0..3]   u32 = 4                      (size 字段长度)
  [4..7]   u32 = 8 + 头部 pickle 长度
  [8..11]  u32 = 头部 pickle 长度
  [12..15] u32 = 头 JSON 字符串长度 jlen
  [16..16+jlen)  头 JSON (UTF-8)
  [(16+jlen) 向上对齐到 4 字节)          (填充)
  [对齐后..]  各文件数据依次排列
```

重打包算法(与官方 asar 产物字节级兼容,已被 1.14.9 实证):

1. 按原头 JSON 顺序取出每个文件的 `{size, offset, integrity}`(offset 是**字符串**),
   按 `dataOff + offset` 切出内容;
2. 修改内容(注入/字节补丁),必要时**追加新文件**(见 §8.3);
3. 重建 entries:`{size: 新长度, offset: String(累计偏移), integrity: 完整性对象}`——
   **integrity 的字段 schema 必须照抄原头**(1.14.9 为
   `{algorithm:"SHA256", hash:<各4MB分块sha256 hex依次拼接>, blockSize:4194304, blocks:[...]}`,
   文件小于一块时 hash 即单块哈希);
4. `JSON.stringify({files: entries})`(紧凑、无空格、保持键序),得头 JSON;
5. 写 16 字节 pickle 头 + JSON + 4 字节对齐填充,再拼接全部文件数据;
6. **exe 内嵌哈希 = sha256(头 JSON 字符串本体)**——不含对齐填充(已实证)。

### 4.2 exe 哈希替换

latin1 读写全文 → §2.1 的正则原位替换 → **断言长度不变** → 原子写
(先写 `.new` 再 rename,防中断产生半文件)。

## 五、验证方法论(适配新版本时唯一可信的依据)

### 5.1 调试基础设施先行

补丁模块内置环境变量开关(如 `TYPORA_PATCH_DEBUG=1`),日志写 `%TEMP%\*.log`。
要观察的关键行:

```
patch_main loaded          ← 注入生效
fs hooked / electron hooked / native-reg hooked
override IDate ...         ← 试用起点虚拟化生效
blocked license window     ← 许可窗口被拦截
launch.dist.js -> pristine ← 应用自检拿到原始内容 (抗自检生效)
```

### 5.2 行为验证清单

- [ ] 正常启动,无许可/购买弹窗(启动即弹的那种)
- [ ] **等 60~90 秒**:水印/角标类延迟注入的 UI 不出现(此类常延迟 30~60 秒)
- [ ] 新建/另开窗口,同样干净(每个窗口可能独立注入)
- [ ] 把试用起点改成过期日期再启动 → 日志显示被虚拟化、应用照常满试用
- [ ] 正常编辑功能可用,连续打开多个文件正常
- [ ] 长时间运行不退出(防"藏窗口"误杀主窗口)

### 5.3 版本适配时的否证顺序

补丁后启动即退 → 按序排查:① 日志有无 `Integrity check failed`(自检没喂到原始内容
→ 检查 fs 钩子路径匹配与标记剥除正则);② exe 内嵌哈希是否与新 asar 头一致
(重算);③ 注入是否语法错误(把注入后的入口文件单拎出来 `node --check`);
④ jsc 锚点替换是否破坏了别的常量(回滚 jsc 单独测试)。

## 六、一键 bat 的通用知识

### 6.1 编码与语法(中文 bat 两大坑)

1. **必须 GBK + CRLF**。UTF-8/LF 的 bat 会被 cmd 解析错乱:症状是命令在任意位置
   被截断(`'ODE_EXE' 不是内部或外部命令`、`'4.' 不是…`)。生成方式建议脚本化
   (python 以 `encoding="gbk", newline="\r\n"` 写出),**不要手工编辑**;
   纯 ASCII 文案是更稳的替代(代价是没有中文提示)。
2. `if (...)` / `for (...)` **括号块内的 echo 文本不能含未转义圆括号**
   (如 `(https://example.org)`),`)` 会提前闭合块,报 `此时不应有 …`。
   要么去掉文案括号,要么转义 `^(` `^)`。

### 6.2 结构模板(自动探测 + 幂等 + 可还原)

```bat
@echo off
setlocal EnableExtensions
rem 1) 找 node: where node → %ProgramFiles%\nodejs → 注册表 InstallPath
rem    (reg query "HKLM\SOFTWARE\Node.js" /v InstallPath) → nvm 目录 for /d 扫描
rem 2) 找应用: 参数 %1 → 常见安装路径 → set /p 手动输入 (剥引号)
rem 3) taskkill /f /im <App>.exe (忽略错误) + 短暂等待
rem 4) node patch.js "<目录>";if errorlevel 1 (报错 + pause + exit /b 1)
rem 5) start "" "<目录>\<App>.exe" + pause
```

经验点(来自 1.14.9 实测):

- 注册表 `InstallPath` 可能是**安装器残留**(指向的目录里根本没有 node.exe),
  探测后必须 `if exist` 验证;nvm 目录扫描(`for /d`)是可靠的兜底;
- 幂等设计:补丁脚本用正则剥掉旧注入再重新注入;字节补丁"已补则跳过";
  备份"已存在则不覆盖";
- 所有出错路径都要 `pause`,避免双击运行时窗口闪退看不到报错;
- **复杂逻辑不要写进 bat**:bat 只做"找路径 + 关进程 + 调脚本 + 启动",
  补丁本体放 node/python(脚本文件而非命令行内联,见 §7.4 引号教训)。

## 七、预打补丁安装包(Inno Setup 通用流程)

### 7.1 识别原版安装器类型

| 特征 | 类型 | 应对 |
|---|---|---|
| `unins000.exe` / `unins000.dat` | **Inno Setup** | 用 Inno 重打包(下文) |
| `uninst.exe` + nsis 特征 | NSIS | makensis(单文件, 免安装) |
| `.msi` | MSI | WiX 或保持原 MSI 结构 |
| `Update.exe` / squirrel | Squirrel | nupkg 结构, 较特殊 |

### 7.2 获取免安装的 Inno 编译器(绕开 UAC)

**问题**:自动化环境(非提权 shell)运行任何 admin 安装器都会被 UAC 拦:
实测 Inno 6.7.3 `/VERYSILENT` 返回 exit=2 且无日志;7-Zip `/S` 报
"操作已被用户取消"。

**通用解法:innoextract 链路**(全部免安装、免提权):

1. 下载 [innoextract](https://github.com/dscharrer/innoextract)(单 exe);
   **版本支持上限**:1.9 支持 Inno ≤ 6.0.5(用 `innoextract -l <安装器>` 试探,
   能列出文件即支持);
2. 从 GitHub `jrsoftware/issrc` 的 tag(命名 `is-6_0_5` 形式)下载与目标匹配的
   `innosetup-<版本>.exe`;
3. `innoextract -d <目录> innosetup-<版本>.exe` → `<目录>\app\ISCC.exe` 直接可用。
4. 编译器版本选择:**与原版安装器同大版本**最稳(1.14.9 原版是 6.0.0 → 用 6.0.5 编译)。

### 7.3 复刻原版安装行为(取证三件套)

1. **文件清单**:`innoextract -l <原版安装器>`(得到全部文件与相对路径);
2. **AppId**:在装过原版的机器读卸载表
   `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\{GUID}_is1`,
   **沿用同一 GUID** → 覆盖安装、共用卸载入口;
   (没有现成机器时:装到虚拟机/沙箱读一次即可)
3. **文件关联与快捷方式**:`reg export` 逐键导出(ProgID、扩展名 OpenWithProgids、
   PerceivedType),并检查 `Public Desktop` / Start Menu 的 .lnk;
   **例**:Typora 原版注册 6 个 ProgID + 6 个扩展名映射,**不**注册协议处理,
   只建公共桌面快捷方式(无开始菜单项)——这些细节决定"装起来像不像原版"。

### 7.4 .iss 要点(模板化)

```iss
[Setup]
AppId={{<沿用原版GUID>}              ; {{ 转义花括号
DefaultDirName={autopf}\Typora       ; 原版装哪就写哪
ArchitecturesInstallIn64BitMode=x64
PrivilegesRequired=admin             ; 正式版; 测试变体用 lowest
Compression=lzma2/max
SolidCompression=yes
SetupIconFile=<stage>\resources\assets\installer.ico

[Files]
Source: "<stage>\*"; DestDir: "{app}"; Flags: ignoreversion recursesubdirs createallsubdirs

[Icons]
Name: "{autodesktop}\Typora"; Filename: "{app}\Typora.exe"   ; 按取证结论

[Registry]                            ; 按取证结论逐条翻译 reg 导出
Root: HKLM; SubKey: "SOFTWARE\Classes\Typora.md"; ValueType: string; ValueName: ""; ValueData: "Markdown File"; Flags: uninsdeletekey
Root: HKLM; SubKey: "SOFTWARE\Classes\Typora.md\shell\open\command"; ValueType: string; ValueName: ""; ValueData: """{app}\Typora.exe"" ""%1"""
Root: HKLM; SubKey: "SOFTWARE\Classes\.md\OpenWithProgids"; ValueType: string; ValueName: "Typora.md"; ValueData: ""; Flags: uninsdeletevalue

[Run]
Filename: "{app}\Typora.exe"; Flags: nowait postinstall skipifsilent
```

**双 .iss 测试法**(在没有提权 shell 的机器上验证安装包):

- 正式版:`PrivilegesRequired=admin` + HKLM 关联(发布用);
- 测试版:`PrivilegesRequired=lowest`、去掉 [Registry]、图标用 `{userdesktop}`
  → 可 `/VERYSILENT /DIR=<临时目录>` 静默装到任意可写路径,完整走一遍
  安装-启动-验证,而无需点 UAC。

### 7.5 安装包内容:--bundle 模式(消除机器依赖)

就地补丁注入的是补丁模块的**绝对路径**,换机器即失效。通用做法:

1. 打包模式给补丁脚本加开关(如 `--bundle`):
   注入改为**相对路径** `require("./patch_main.js")`,并把补丁模块作为**新文件
   打进 asar**(asar 的 require 由 Electron 的 asar fs 支持,内部相对引用无碍);
2. 抗自检的"标记剥除"必须同时兼容绝对/相对两种注入形态 → 用正则而非精确串:
   `/require\((["'])[^"']*patch_main\.js\1\),/g`;
3. 打包模式跳过备份(stage 树从纯净原件构建,备份无意义);
4. 重建流程三步(参数化):

```bat
:: 1) 把<新版>干净安装树放进 stage\app (不含卸载器/备份)
:: 2) bundle 模式补丁
node <补丁目录>\patch_typora.js <stage\app> --bundle
:: 3) 编译
<ISCC目录>\ISCC.exe <脚本>.iss
```

## 八、工程化通用原则(贯穿所有脚本)

1. **锚点校验 + 宁可中止**:所有搜索/替换必须"找不到就报错退出",绝不静默跳过
   或写坏文件;锚点定位用"长字符串 → 前置窗口内找结构"两段法。
2. **幂等**:旧注入先剥(正则)、字节补丁"已补则跳过"、备份"存在则不覆盖"——
   重复运行结果一致。
3. **原子写**:先写 `.new` 再 rename;exe 断言长度不变。
4. **备份策略**:同目录 `原名.backup.<时间戳>`,**时间戳最早的一对是纯净原版**,
   还原后其余可删。
5. **脚本文件而非命令行内联**:shell 嵌套引号极脆弱(实测 bash -c 内 heredoc 被
   外层解析破坏,解释器进入交互模式死循环)。凡两步以上的逻辑一律落盘为
   .py/.ps1/.sh 再执行。
6. **环境差异兜底**:node/应用路径探测永远"多来源 + if exist 验证",
   注册表残留值不可信。
7. **日志可追溯**:补丁模块带 DEBUG 开关;重要脚本输出关键决策(备份路径、
   新哈希、替换前后值)。

## 九、通用故障排查矩阵

| 现象 | 根因 | 处理 |
|---|---|---|
| 启动 1 秒左右自动退出 | 应用自检没被喂到原始内容 / exe 哈希与新 asar 不配套 | 查 §5.3 否证顺序 |
| 补丁脚本报"锚点…中止" | 版本不符或结构变化 | 确认版本;按 §三 重找锚点 |
| 钩子日志有 `Cannot assign to read only property` | 原生模块首个实例 exports 冻结 | 预期噪声;以"override 生效"日志为准 |
| bat 乱码/命令被截断 | bat 编码不是 GBK+CRLF | 用脚本重新生成 bat,勿手工编辑 |
| bat 报 `此时不应有 …` | if/for 块内 echo 文本含圆括号 | 去括号或转义 |
| bat 找不到 node | 注册表 InstallPath 残留指向空目录 | 探测后 if exist 验证;nvm 扫描兜底 |
| 安装包双击无反应/静默失败 | UAC 拦截 admin 安装 | 提权运行;或先用 lowest 测试变体排错 |
| 装机后行为不对 | 安装包里是绝对路径注入(未用 bundle 模式) | 用 `--bundle` 重建 |
| 用一段时间后弹窗/水印回归 | 应用自动更新覆盖了文件 | 关自动更新;重跑补丁 |
| innoextract 报 loader revision 不识别 | 原版安装器用的 Inno 版本超出其支持 | 换支持上限更高的 innoextract,或 7-Zip 21.07+ |
| 编译出的安装包与原版行为不一致 | AppId/关联/快捷方式未取证 | 按 §7.3 三件套重新取证 |

## 十、术语与速查

- **asar**:Electron 归档格式;头是 pickle 包裹的 JSON 文件表,数据区按 offset 排布;
  offsets 在 JSON 里是字符串;头 JSON 的 sha256 即 exe fuse 校验值。
- **jsc / cachedData**:V8 字节码缓存,自带长度与哈希自描述——只能同长度字节替换,
  不能变长、不能重排。
- **fuse**:Electron 编译进 exe 的一组行为开关(含 asar 完整性校验、
  RUN_AS_NODE 禁用等),二进制层面定位搜 `ELECTRONASAR`/`INTEGRITY`。
- **试用起点虚拟化**:不碰真实存储,仅在读取函数出口处把"起点"替换为"今天"——
  兼容存储格式变化,也避免应用启动时重写状态导致失效。
- **工具链获取速查**:innoextract → `github.com/dscharrer/innoextract`(release 单文件);
  Inno Setup 各版本安装器 → `github.com/jrsoftware/issrc/releases`(tag 形如 `is-6_0_5`)
  或 `files.jrsoftware.org/is/6/`(新版才有);7-Zip → `github.com/ip7z/7zip`。
- **日志开关约定**:`<应用>_PATCH_DEBUG=1` → `%TEMP%\<应用>_patch.log`。

## 十一、随附通用工具(tools\ 目录,任意版本/机器可用)

纯 Python 3 标准库实现(无第三方依赖、无硬编码路径),随补丁目录一起拷贝。
在本项目 1.14.9 asar 上做过往返一致性验证(解包→重打包,头哈希逐字节不变)。

### 11.1 find_anchors.py — 新版本适配前侦查(对应阶段①②③)

```
python find_anchors.py <Typora安装目录>
```

一次性回答"现有补丁流程能不能直接用于这个版本":

1. 基本结构(主 exe / resources\app.asar);
2. asar 文件清单 + package.json 入口与版本号;
3. 入口 JS 的注入锚点(`require("./xxx.jsc");` 形态)是否存在;
4. 各 .jsc 内全部特征串锚点(许可页路由、试用起点、试用天数、水印文字、
   水印赋值/条件锚、应用自检特征)——给出偏移、命中次数与上下文;
5. exe 内嵌完整性校验串:是否存在、与 asar 实际头哈希是否一致
   (一致=纯净或已同步,不一致=exe 与 asar 不配套,启动必挂)。

退出码 0=锚点齐备可直接套现有流程;1=有缺失,按 §三 重新设计锚点。
**JSC_ANCHORS 字典在脚本头部,新版本特征变化时在此追加即可。**

### 11.2 asar_tool.py — asar 通用四合一(对应阶段④)

```
python asar_tool.py list    <asar>                        # 文件清单+偏移
python asar_tool.py extract <asar> <输出目录>             # 解包
python asar_tool.py repack  <原始.asar> <文件目录> <输出>   # 以原头为模板重打包
python asar_tool.py hash    <asar>                        # 头 JSON 的 sha256
```

要点:

- `repack` 以**原始 asar 的头为模板**:保持文件顺序与目录结构(支持嵌套),
  逐文件 integrity 的 `algorithm`/`blockSize` 照抄原头、`hash`/`blocks` 按
  新内容重算——这就是"schema 照抄、内容重算"原则的落地实现;
- 头 JSON 用紧凑序列化(与 Node `JSON.stringify` 一致,UTF-8 不转义),
  打印的"新头哈希"即 exe 内嵌校验值应写入的 sha256;
- `hash` 用于比对 exe 内嵌值,判断 asar/exe 是否配套;
- repack 严格要求文件集合与原头一致,多文件/缺文件都会报错中止。

### 11.3 与补丁脚本的关系

- `patch_typora.js` 内嵌了同样的 asar 解析/重打包逻辑(针对 Typora 一体化)。
  这两个工具是**通用版**:analyse 任意版本、验证往返、或手动做补丁实验时用;
- 补丁本体仍以 `patch_typora.js`/`patch_main.js` 为准(带锚点校验与幂等);
- 工作区 `..\winpatch\` 里的 `gen_patch_bat.py`(生成 GBK 版 patch.bat)、
  `dump_reg.ps1`(取证用 reg export 批量导出)、两个 `.iss`(安装包脚本)为
  本项目构建产物,同样是可复用的模板。
