## 一、起点与总体思路

- 已有 macOS 版补丁 `../../macos/`:对 Mach-O 里 `LicenseManager` 三个方法
  (`cannotContonueUse:` / `showLicense:` / `showLicenseIfNeeded:`)做 ARM64 二进制补丁。
- 目标:Windows 版(`<Typora安装目录>`)达到同等效果。
- Windows 版是 **Electron 42.2.0**(Chromium 148 / V8 14.8),主逻辑不在 exe 里:
  - `resources/app.asar` 仅 3 个文件:`package.json`、`launch.dist.js`(明文 JS 入口)、
    `atom.compiled.dist.jsc`(主进程 **V8 编译字节码**,bytenode 风格加载,不可直接编辑)
  - `launch.dist.js` 里有 `Module._extensions[".jsc"]` 加载器,最后
    `require("./atom.compiled.dist.jsc")`
- 因此路线定为:**明文 JS 入口注入 + 运行时 JS 钩子**,对齐 Mac 三个补丁点。

## 二、侦查:两层完整性校验(必须先解决,否则一切白搭)

1. **Electron fuse 层**: `Typora.exe`(227MB)内嵌 PE 资源 `ELECTRONASAR`/`INTEGRITY`,
   内容 `[{"file":"resources\\app.asar","alg":"SHA256","value":"<64位hex>"}]`,
   值 = **asar 头 JSON 字符串的 sha256**。改 asar 后必须定长原位替换(latin1 读写,
   不改 PE 结构、不改文件长度)。
2. **应用自检 `[LC]`**: 启动约 1 秒后主进程读 `app.asar/package.json` 与
   `launch.dist.js` 做完整性比对,失败记 `Integrity check failed` 并退出。
   对策:fs 钩子(`readFileSync` + `promises.readFile`)对 launch.dist.js 返回
   **剥掉补丁标记的"原始"内容**。
3. 其他封死的路(都试过/查过):`ELECTRON_RUN_AS_NODE` 被 fuse 禁用;
   `resources\app` 目录模式被拒 —— 只能走 asar+exe 哈希这条唯一通道。
4. asar 重打包是**手写复刻**:解析头(4×u32 pickle + JSON),保持文件顺序,
   逐文件算 4MB 分块 SHA256 完整性块,头 JSON 重新序列化、4 字节对齐、重算头哈希。

## 三、许可补丁(Mac 三补丁的 Windows 对应实现)

| Mac 补丁 | Windows 实现 | 关键发现 |
|---|---|---|
| 1 `cannotContonueUse:` 恒 0 | 拦截 `Module._load` 给 `native-reg` 模块的 `getValue/queryValue` 打钩,读到值名 `IDate`(试用起点)时恒返回当天 `M/D/YYYY` | 试用状态在 `HKCU\Software\Typora`(IDate/SLicense);到期表现为 `dayRemains=0` |
| 2/3 `showLicense…` 静默 | 拦截 `BrowserWindow.loadURL`,丢弃 `license.html` 加载并**隐藏空壳窗口**(setTimeout hide + setSkipTaskbar,再钩 `show`) | 不能 destroy——会触发 `window-all-closed` 导致整个应用退出;`webContents.loadURL` 也要一起拦 |

验证方式:把注册表 `IDate` 故意改成 `9/4/2025` 后启动,调试日志
(`TYPORA_PATCH_DEBUG=1` → `%TEMP%\typora_patch.log`)确认:
`override IDate | 9/4/2025 -> 9/4/2026`、`blocked license window …dayRemains=15`、
`suppressed show of license shell`、`launch.dist.js -> pristine`,应用正常使用。

## 四、水印攻坚(最费周折的部分,按时间线记录)

1. **现象**:启动/新窗口约 30~60 秒后,左下角出现"未激活 ×"可点击按钮
   (点击会打开许可窗口)。每个新窗口都会注入一次。
2. **第一轮尝试(失败)**:把所有可能的注入通道都挂了钩——
   `webContents.executeJavaScript`、`WebFrameMain.executeJavaScript`(过滤含
   `UNREGISTERED` 的代码)、DEBUG 模式记录 `wc.send` 全部通道——按钮照样出现,
   **传输通道始终没抓到**。
3. **换思路(成功)**:注入代码本体就嵌在 `atom.compiled.dist.jsc` 字节码里
   (onUnfillLicense 片段,常量池含 `UNREGISTERED`、`File.option.hasLicense = false;`)。
   字节码不可重编译,但可以做**同长度字节补丁**:
   把片段条件 `if(window.File.option){` 改成 `if(window.File.optio0){` ——
   `optio0` 是 undefined 恒 falsy,整段创建水印的代码静默跳过,与传输通道无关。
   锚点定位:先找 `File.option.hasLicense = false;`,再在其前 64 字节内找条件串;
   幂等(已补过则跳过);两处锚点都对不上时**中止**而不是打坏文件。
4. **验证**:首窗口运行 50 秒+(旧版约 40 秒必现)无按钮;Ctrl+N 新开窗口同样干净;
   截图目视确认左下角。`patch_main.js` 里的通道过滤保留作双保险。

## 五、patch.bat 一键脚本(两个经典坑)

- 功能:自动找 Node(PATH → Program Files(x86) → 注册表 `Node.js` InstallPath →
  nvm 目录扫描)→ 自动找 Typora(常用路径,失败则提示输入)→ 关进程 → 调
  `patch_typora.js` → 成功后启动 Typora。
- **坑 1(编码)**:中文 .bat 必须存 **GBK + CRLF**。UTF-8/LF 会让 cmd 解析错乱,
  表现为命令被随机截断(`'ODE_EXE' 不是内部或外部命令` 之类)。
  现由 `winpatch\gen_patch_bat.py` 生成,别手改。
- **坑 2(括号)**:`if (...)` 块内的 `echo` 文本不能含未转义圆括号
  (如 `(https://nodejs.org)`),`)` 会提前闭合 if 块,报 `此时不应有 …`。
  已把块内提示文案的括号全部去掉。
- 本机注册表 `HKLM\SOFTWARE\Node.js` 的 InstallPath 指向的目录里**没有** node.exe
  (安装器残留),实际 node 在 `<nvm目录>\v26.8.1\`,所以扫描顺序里
  nvm 目录是兜底关键。bat 已在本机端到端实测(含幂等重跑)。

## 六、预打补丁安装包(免 Node,装完即用)

### 6.1 方案选择

- 原版安装器 `typora-setup-x64.exe`(113,693,176 字节)是 **Inno Setup** 打包
  (`unins000.exe` 特征),故选 Inno Setup 重打包,行为最接近原版。

### 6.2 工具链获取(全程绕开 UAC)

- 本机 shell **非提权**,静默装任何 installer 都会被 UAC 拦(实测:Inno Setup
  6.7.3 安装器 `/VERYSILENT` 得 exit=2 且无日志;7-Zip `/S` 直接"操作已被用户取消")。
- 解法:**innoextract 1.9**(单文件免安装,`dscharrer/innoextract` GitHub release)
  —— 它能把 **Inno Setup 自己的安装器**当数据解包。
- 原版安装器被 innoextract 识别为 `setup data version 6.0.0 (unicode)`,
  而它只支持 ≤6.0.5 → 恰好从 GitHub `jrsoftware/issrc` tag `is-6_0_5` 下载
  `innosetup-6.0.5.exe`,解包得到 `winpatch\inno605\app\ISCC.exe`(免安装可用)。
  注意:新版 Inno(6.7)安装器 loader revision 变了,innoextract 1.9 读不了。
- 教训:shell 里嵌套引号极易翻车(bash -c 内 heredoc 被外层 cmd 破坏,python 进入
  交互模式死循环)。**复杂操作一律写成 .ps1/.py/.sh 脚本文件再执行。**

### 6.3 复刻原版安装行为(证据来源)

- `innoextract -l`:原版 412 个文件全在 `app\` 下;语言仅 english。
- **AppId** 取自本机卸载表:`HKLM\…\Uninstall\{37771A20-7167-44C0-B322-FD3E54C56156}_is1`,
  与官方一致 → 覆盖安装/共用卸载入口。
- **文件关联**:用 `reg export` 导出(结果在 `winpatch\orig_registry\`):
  6 个 ProgID(`Typora.md/.markdown/.mdown/.mkd/.mmd/.text`,DefaultIcon 指向
  `resources\assets\file.ico`,open 命令 `"…Typora.exe" "%1"`,AppUserModelID
  `abnerworks.Typora`)+ 6 个扩展名的 `OpenWithProgids`(.text 另有
  `PerceivedType=text`)。**原版不注册 typora:// 协议、无 Capabilities/RegisteredApplications**。
- **快捷方式**:本机只有 `C:\Users\Public\Desktop\Typora.lnk`,无开始菜单项
  → .iss 只做 `{autodesktop}` 图标。

### 6.4 --bundle 打包模式(安装包能装到任意路径的关键)

- 就地补丁模式往 launch.dist.js 注入的是 patch_main.js 的**绝对路径**,换机器即失效。
- 新增 `node patch_typora.js <目录> --bundle`:
  - 注入 `require("./patch_main.js")` 相对路径;
  - `patch_main.js` 作为**第 4 个文件打进 app.asar**;
  - 跳过备份(stage 树从纯净原件构建);
  - `patch_main.js` 的标记剥除由精确串匹配改为**正则**
    `/require\((["'])[^"']*patch_main\.js\1\),/g`,同时兼容绝对/相对两种注入形态
    ——[LC] 自检因此通过(日志 `launch.dist.js -> pristine` 实证)。
- stage 树来源:`installed\` robocopy 排除 `unins000.*`、`Typora.exe`、`app.asar`,
  再用 `*.backup.20260904052906`(最纯净原版)覆盖后两个文件。

### 6.5 构建与验证

- staging 直接启动验证:补丁从 asar 内加载、[LC] 过、IDate 覆盖、许可窗口拦截。
- 双 .iss 策略:`typora_patched.iss`(正式,admin + HKLM 关联)与
  `typora_patched_test.iss`(PrivilegesRequired=lowest、无注册表)——
  后者用于在**非提权 shell** 里 `/VERYSILENT /DIR=…` 真实走一遍安装。
- 测试版静默安装 exit=0(413 文件),启动后全部补丁行为正常;
  **65 秒水印观察干净**;随后正式版编译约 60 秒成功。
- 产物 `Typora_1.14.9_Patched_Setup.exe`(113,709,407 字节,与原版几乎同尺寸)
  交付到 `<项目根目录>\`;测试产物已清理,本机 `installed` 版恢复运行。

### 6.6 已知无害告警(留档,别误判为故障)

调试日志里有一行 `hook error: Cannot assign to read only property 'getValue'`:
native-reg 第一个被 require 的模块实例(其 index.js 出口)exports 被冻结,赋值失败
被 try/catch 吞掉;真正的绑定模块在后续 `_load` 命中时成功挂钩
(紧接着的 `override IDate` 日志即证明生效)。属预期内的兼容行为,不影响功能。

## 九、2026-10-15 追加排查:"新建/新建窗口"被静默锁死

### 现象

用户报告「文件→新建」「文件→新建窗口」点了完全没反应(不报错、无窗口)。
同时期还出现过"双击桌面图标打不开 / 有进程但看不到窗口"。

### 排查链条

1. **先排除补丁误伤**:逐行核对 `patch_main.js` 的钩子(`loadURL` 只拦
   `license.html`;`executeJavaScript` 只拦含 `UNREGISTERED` 的代码;
   `show` 只拦被标记的许可空壳)——都不涉及新建/新窗口逻辑。
2. **看应用日志**发现两条硬证据:
   - `typora.log` 里 Ctrl+N 触发 `app.openFile` 后报
     `Error occurred in handler for 'app.openFile'` +
     `MaxListenersExceededWarning: 11 did-stop-loading listeners`(行为被拒绝的痕迹);
   - 补丁调试日志:`override IDate | 9/4/2026 -> | 10/15/2026`(注册表覆盖成功),
     但下一步 `blocked license window: …dayRemains=0…` 且
     `typora.log: [L] installDate is 9/4/2026, trail remains: 0 days`。
3. **结论**:试用被判过期。Typora 在试用过期时会禁用"新建/新建窗口"这类操作,
   而它想弹的许可提示窗口被本补丁藏掉了 → 表现为"点了没反应"。
4. **为什么覆盖失效**:注册表 `IDate` 确实被改成今天了,但试用天数用的是**另一份**数据。
   在 jsc 字符串里找到线索:`writeInstallDate fromBTime=`、
   `[L] Read from incorrupted InstallDate`、`…/profile.data`。
   解码 `%APPDATA%\Typora\profile.data`(它是 **hex 编码的 JSON**)发现
   `"_iD":"9/4/2026"` = 权威安装日期。
5. **验证**:直接改 `_iD` 为当天 → 日志立刻变成
   `installDate is 10/15/2026, trail remains: 15 days`;Ctrl+N 成功新建
   (窗口标题变为 `Untitled? - Typora`),Ctrl+Shift+N 成功新建窗口
   (日志出现新的 `RenderProcess 4`)。

### 修复

`patch_main.js` 新增第 5 个作用点:对 `profile.data` 的 **fs 读与写双向**
强制把 `_iD` 改成当天。
坑:第一版只处理了 Buffer,日志显示只有 "on write" 命中而 "on read" 不命中 ——
Typora 是用**带 encoding 的 `readFileSync`**(返回 string)读的,
两种类型都处理后才生效。

### 顺带发现(有复用价值)

- **Typora 主动拒绝调试启动参数**:传 `--remote-debugging-port` 会弹
  `Arguments not allowed debug in production main thread` 错误框。
  因此想用 CDP / REA 的 Electron 实时检查能力排查 Typora 是走不通的,
  排查应改用 `TYPORA_PATCH_DEBUG=1` 日志 + 窗口/进程枚举 + 状态文件解码。
- **窗口"看不到"的两类原因**:最小化(rect 为 -32000)或在前台被判过期后状态异常;
  枚举窗口时要包含**隐藏窗口**(`EnumWindows` 不过滤可见性),
  否则会误判"没有窗口"。
- 排查中的临时脚本已在事后清理,保留 `enum_windows.ps1`(窗口枚举)、
  `logtail.ps1`(日志尾巴)、`rebuild_installer.ps1`(重建安装包)三个常用件。

## 十、2026-10-15 追加:Typora 升级到 1.14.10 的兼容性核对

### 背景

用户把 Typora 从 1.14.9 自动更新到 **1.14.10**。更新会替换 `Typora.exe` 与
`resources/app.asar`,补丁随之失效 —— 需要确认既有方法是否还能直接用,
以及"不同版本是否要用不同方法"(本文档的结论性回答见下)。

### 核对过程与证据

1. **结构**:新版 `app.asar` 仍是 3 文件(`package.json` / `launch.dist.js` /
   `atom.compiled.dist.jsc`),`package.json` 的 version 由 `1.14.9` →
   `1.14.10`,releaseId `be82b3a0` → `49b5981e`。
2. **入口文件逐字节比对**:把 1.14.9 的纯净 asar(备份 `*.backup.20260904052906`)
   与新版一起解包比对 —— `launch.dist.js` **长度与 sha256 完全相同**
   (1381 B / `3ec9df88…`),零差异块。说明注入锚点一字未变。
3. **jsc 锚点**:`find_anchors.py` 对新版全绿:许可页路由 `license.html`、
   `IDate`、`dayRemains`、`UNREGISTERED`、水印赋值锚
   (`File.option.hasLicense = false;`)与条件锚(`if(window.File.option){`)全部命中;
   整体偏移比 1.14.9 小约 8 字节(文件 388352 → 388344 B),结构未变。
4. **exe 内嵌校验串**:格式与 1.14.9 相同(仅 value 不同),且新版自带的
   内嵌哈希与 asar 实际头哈希一致(纯净态)。
5. **试用状态来源**:仍未变 —— 注册表 `IDate` + `profile.data` 的 `_iD`
   (profile.data 里 uuid 与版本号也一并更新,`_iD` 字段沿用)。
6. **实打**:`node patch_typora.js <新版目录>` 一次通过(注入/水印字节补丁/
   重打包/exe 哈希替换),备份 `*.backup.20261015125915`。
7. **运行时验证**(`TYPORA_PATCH_DEBUG=1`):hook 日志四条全中 ——
   `profile.data _iD -> today on read`、`override IDate`、
   `blocked license window`、`launch.dist.js -> pristine`;
   `typora.log` 显示 `trail remains: 15 days`(此时磁盘上 `_iD` 故意留成 9/4/2026);
   `Ctrl+N` 触发新文档(`RenderProcess 3` + `added recovery 3`),无许可弹窗。

### 结论(回答"不同版本是否要用不同方法")

**不需要。** 1.14.9 → 1.14.10 是"只改主逻辑字节码内容"的常规更新:
`launch.dist.js` 逐字节相同、jsc 锚点结构不变、完整性机制不变、状态来源不变,
补丁脚本**未改一行代码**即可套用。

一般规律(写进 `通用方法论.md` §12):升级后是否需要改方法,取决于**变化落在哪一层** ——
锚点偏移变化不用管(脚本自带校验);锚点字符串改写要更新锚点常量;
入口/完整性机制/状态来源变化才需要改方法。
